# Glidepath: known gaps

Found in use on 2026-09-26/27 while building `baggage-api` and the values-validation gate. Each has a reproduction or
evidence, so they can be picked up later without re-deriving them. Roughly ordered by how much they cost.

| # | Gap | Evidence | Direction |
|---|---|---|---|
| 1 | **Image version has no Python support.** `build-image` takes the version from a git tag, then `package.json`, then `pom.xml`, else `0.0.0`. A Python app is always `0.0.0-<sha>`. | `baggage-api` images are `0.0.0-893e163`; `boarding-api` is `1.1.0-8f9acd9`. | **Fixed and live-verified 2026-09-27.** `jfillman/glidepath#2` (build-image reads `pyproject.toml`'s `[project] version` via `yq -p toml`, falls back to a plain `VERSION` file) and `jfillman/airframe#5` (pythonapplication's pip branch scaffolds a `VERSION` file) both merged; airframe tagged `v0.3.94` and the pin bumped in `apron`/`glidepath`/`gitops-cluster-dev`, synced on `kiac-dev`. Composition reconciled, committed `baggage-api`'s `VERSION` (`0.1.0`) straight to `main`, a real build ran, and the resulting `image-ref` is `ghcr.io/jfillman/baggage-api:0.1.0-ae82839` - deployed to dev. `boarding-api`/`flight-api` will pick up the same fix on their next resync. |

| 24 | **Go apps have no version-injection path.** Unlike Node/Python/Maven, Go has no manifest-embedded version convention - `build-image`'s VERSION-resolution precedence chain falls through package.json/pom.xml/pyproject.toml for a Go app and lands on a `VERSION` file or literal `0.0.0`, and even when a git tag resolves a real VERSION, nothing injects it into the compiled binary itself (no `-ldflags -X` anywhere in the build path) - `payment-api --version` (or equivalent) can't report anything meaningful. | Confirmed via `build-image.yaml`'s precedence chain: no `go.mod`-aware branch exists, and `build-source.yaml`/app Containerfiles have no version-injection convention. | **Fixed 2026-09-29:** `build-image.yaml` now passes `HANGAR_VERSION`/`HANGAR_GIT_REVISION` as kaniko `--build-arg`s unconditionally on every build (not gated by a schema field - a Containerfile that doesn't declare a matching `ARG` sees no effect). Deliberately generic rather than Go-specific: any language's Containerfile can consume the same two args. See `docs/user/cicd-yaml-reference.md`'s new "Version metadata inside the image" section for the Go `-ldflags -X` recipe. Not yet exercised against a real Go app's Containerfile - schema/render-verified only (`helm template`), no live TaskRun yet. |
