# Glidepath: known gaps

Found in use on 2026-09-26/27 while building `baggage-api` and the values-validation gate. Each has a reproduction or
evidence, so they can be picked up later without re-deriving them. Roughly ordered by how much they cost.

| # | Gap | Evidence | Direction |
|---|---|---|---|
| 1 | **Image version has no Python support.** `build-image` takes the version from a git tag, then `package.json`, then `pom.xml`, else `0.0.0`. A Python app is always `0.0.0-<sha>`. | `baggage-api` images are `0.0.0-893e163`; `boarding-api` is `1.1.0-8f9acd9`. | **Fixed and live-verified 2026-09-27.** `jfillman/glidepath#2` (build-image reads `pyproject.toml`'s `[project] version` via `yq -p toml`, falls back to a plain `VERSION` file) and `jfillman/airframe#5` (pythonapplication's pip branch scaffolds a `VERSION` file) both merged; airframe tagged `v0.3.94` and the pin bumped in `apron`/`glidepath`/`gitops-cluster-dev`, synced on `kiac-dev`. Composition reconciled, committed `baggage-api`'s `VERSION` (`0.1.0`) straight to `main`, a real build ran, and the resulting `image-ref` is `ghcr.io/jfillman/baggage-api:0.1.0-ae82839` - deployed to dev. `boarding-api`/`flight-api` will pick up the same fix on their next resync. |
| 2 | **The onboarding resync can report "up to date" when it is not.** For `boarding-api` it said "gitops repo: .tekton/ already up to date, nothing to deliver" while the gitops repo lacked the new `pull-request-values.yaml`; a second run delivered it. Likely it compared against a template ConfigMap that had not refreshed yet. | `onboarding-resync-q8m67` log, 2026-09-27 00:35. | Compare the delivered set against the rendered template set by file name and hash, not by the previous run's state; retry once when the template ConfigMap changed during the run. |
| 3 | **Deploy paths are hardcoded to `platform/envs/<env>.yaml`.** A standalone Glidepath would write an Airframe-shaped file nothing reads. | `deploy-manifests`, `open-release-pr`, the PaC exemption, `ephemeral-envs`, Tower. | `deploy.releaseFile` in `cicd.yaml` (design in Hangar `docs/autopilot/release-file-split.md`). |
| 4 | **An unsigned commit fails the `provenance` gate on an upper release**, and so `image-promotion`. Agent commits are unsigned. | `baggage-api` release PR #2: `commit has no gpgsig`. | Decision D1 (self-hosted Fulcio for agent commits). Meanwhile a clearer message: which commit, and how to sign. |
| 5 | **Config-only pushes are not validated.** Pushes touching only `platform/` or `cicd.yaml` never build, so a human's direct edit of an env file on `main` is checked by nothing. | The exemption in `deliver-onboarding-files`. | A push-triggered validate-only flow for env files, or a required PR path for them. |
| 6 | **Adding a guardrail can hang releases.** `image-promotion` waits for every gate in `releaseGuardrails`; a repo without the gate's `.tekton` file never reports it. | `wait-for-release-guardrails`. | Register a gate only after every gitops repo has the file (documented), or have the wait skip gates a repo does not carry. |
| 7 | **Pull-request pipelines need a `preview` label and do not run on `opened`.** A PR shows no checks until labelled. | `baggage-api` PR #2 had no checks until the label was added. | Say so in the PR comment the platform posts, or run the build on `opened` when the label is already present. |
| 8 | **The webhook path is fragile.** PaC deliveries reach the dev cluster through a temporary tunnel and a `kubectl port-forward`; when the forward died, pushes triggered nothing for about 19 hours with no alert. | Restarted `port-forward 8060:8080` fixed it. | A named tunnel, and an alert on "no PaC event in N hours". |
| 9 | **A namespace can end up with no PipelineRuns at all**, so Tower's Pipelines tab is empty and nothing explains why. | `baggage-api`, before the U4 test. | Keep the last N runs per flow regardless of the pruner, or show "no runs kept" in Tower. |
| 10 | **Tekton steps run as non-root but scripts assume they can chmod a mount root.** `validate-values` failed with `chmod: changing permissions of '/work': Operation not permitted`. Fixed 2026-09-27. | TaskRun log. | Lint Task scripts for chmod/chown on volume roots. |
| 11 | **The values-validation gate depends on the Airframe image tag.** `valuesValidatorImage` must be moved by hand when the chart pin moves. | `glidepath-catalog/values.yaml`. | Derive it from the `airframe-application` chartVersion already pinned in `glidepath-app`. |
| 12 | **`open-release-pr` writes `releaseTracking.relayHostAliasIP` from the dev node's `status.hostIP`**, an address a second cluster cannot route to; the outcome hooks then time out and a new Flight env's first sync fails. | `baggage-api-staging`, 2026-09-27; same as the parked bug in the Skyport handoff. Also listed in Airframe's known gaps. | **Fixed 2026-09-28:** the cluster registry entry takes an optional `relayHostAliasIP` (`glidepath-control-plane` `clusters[]`), and `open-release-pr` uses it when set, `status.hostIP` otherwise. The prod cluster's entry sets `192.168.1.78`. Found again on `gate-api` and `checkin-api` staging, after being fixed by hand several times. |
| 13 | **The values-validation gate hit three Tekton-script bugs on its first real runs** (chmod on the mount root; `workingDir` on a read-only mount; an unpublished validator image tag). All fixed 2026-09-27. | TaskRun logs. | Run a new Task once against a real PR before relying on it; add a fixture-driven test for Task scripts. |
| 14 | **Documented 2026-09-27 (see [github-ruleset.md](github-ruleset.md)); the problems it found are open.** Was: the GitHub ruleset that enforces every guardrail was not documented. It is the thing that makes the checks required, so it is a mandatory install item, yet the docs describe classic branch protection "not IaC-managed" and say nothing of rulesets: scope, required check names (`Pipelines as Code CI / <gate>-`), bypass actors, which repos. `releaseGuardrails` and the ruleset's required list must be kept in sync by hand; a mismatch either never blocks or blocks forever. The GitHub API refuses to show rulesets and branch protection for these private repos to a plain token ("Upgrade to GitHub Pro or make this repository public"), so an export is needed to audit it. | `docs/admin/release-guardrails.md` "Branch protection"; `gh api repos/.../rulesets` returns 403 on the free plan. | Export the ruleset JSON, audit it, document it, and make applying it an install step (ideally generated from `releaseGuardrails`, e.g. a `RepositoryRuleset` from the same list). Note the plan question: rulesets on private repos need a paid plan. |
| 15 | **The required checks assume every PR is a release PR.** All gates run only on `release-*` heads, so onboarding-resync, Tower Config, hand-edit and seed PRs would never satisfy the ruleset's required checks. | Audit of the exported ruleset against every gate's `on-cel-expression`. | Run every gate on every PR and pass immediately for non-release PRs, or add an admin bypass. |
| 16 | **Bots write directly to the gitops default branch** (the composition's `RepositoryFile`s), which a pull-request rule would refuse. | `values-yaml.yaml` in the `ApplicationEnvironment` composition. | Make the writing GitHub App a bypass actor (`--bypass-app-id`). |
| 17 | **`platform/pr-env.yaml` is never scaffolded onto an onboarded app repo**, even though `ephemeral-envs.yaml`'s ApplicationSet has always required it as its second Helm source. Enabling `ephemeralEnvironments.pullRequest.enabled: true` alone is enough to synthesize a working `pr-build` flow and ApplicationSet trigger, but the resulting preview Application sits in `ComparisonError` (`failed to execute helm template command ... no such file or directory`) forever, since nothing ever creates the file. Found live 2026-09-27: `baggage-api-pr-2` (on `kiac-dev`) never provisioned; `boarding-api` and `flight-api` were missing the same file for the same reason. Fixed the 3 known-affected app repos directly (comment-only file, since all 3 apps' container ports already match `airframe-application`'s `rollout.ports` chart default): `jfillman/baggage-api#3`, `jfillman/boarding-api#8`, `jfillman/flight-api#8`. | `baggage-api-pr-2` Application status, `kiac-dev`, `app-baggage-api-cicd` namespace. **Root-cause fix merged and live 2026-09-27.** `jfillman/glidepath#3` merged; the live `deliver-onboarding-files` Task on `kiac-dev` (`platform-catalog` namespace, synced at `fbb99b5`) carries the scaffold step, confirmed by reading its rendered `.spec.steps[].script` directly off the cluster. It scaffolds `platform/pr-env.yaml` once via heredoc, guarded by `[[ ! -f platform/pr-env.yaml ]]`, so a file a developer later edits is never force-overwritten - not re-exercised against a fresh live onboarding-resync run this session (no open PR to trigger one against), but the guard is unconditional and was read directly off the live Task, not just the source. |
| 18 | **Release gates ignored `release.yaml`.** With `deploy.releaseFile` (D9/AF-5) the release lands in a sibling `<cluster>/<env>/release.yaml`, but `extract-promoted-image` and `verify-image-provenance` only diffed `*/values.yaml`, so `image-scan`, `sast`, `sbom` and `provenance` failed with "no */values.yaml changed" on every new app's first release. | `gitops-gate-api` release PR #4, 2026-09-27. | **Fixed 2026-09-27:** both Tasks prefer `*/release.yaml` and fall back to `*/values.yaml`. |
| 19 | **`image-promotion` waited forever on release PRs.** It waits for every gate in `releaseGuardrails`, including `values`, but the `values` gate only triggered when a `values.yaml` changed. With `deploy.releaseFile` a release PR only changes `release.yaml`, so `values` never ran and promotion hung. | `gitops-gate-api` PR #7, 2026-09-28. | **Fixed 2026-09-28:** the `values` gate also triggers on `release.yaml` and passes with a note when no values file changed. Existing gitops repos pick it up through their next onboarding-resync PR. |
| 20 | **The `/retest <gate>` hint in gate comments doesn't re-run anything.** PaC answers "cannot find the targeted pipelinerun sast in this repository": the gates' `on-cel-expression` only matches `release-*` pull_request events, not the retest-comment event. | `gitops-gate-api` PR #4, 2026-09-27; PaC controller log. | Match the retest-comment event in each gate's CEL, or change the hint to closing and reopening the PR, which does re-run them. |
| 21 | **Tower shows a crash-looping rollout as "Progressing" with no diagnosis.** The Deployments tab matched no known issue and listed the pods as running while they were in `CrashLoopBackOff` (a readiness probe on `/` returning 404). | `checkin-api` dev, 2026-09-28. | Surface container restart counts and the last probe failure in Tower's diagnosis rules. |
